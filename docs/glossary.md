# Glossary

The Studio's web interface and the messages of `ut` exist in English and in Italian, and `ut` changes language with `--lang en` or `--lang it`; the code and the API are in English. The table keeps the two languages together. For each entry it gives the term as it appears on screen or in this documentation, the name it carries in the code or in a route, its meaning in one sentence and the Italian term. The Italian term follows the wording of the Italian interface wherever the Studio names the concept; after it, in quotation marks, come the Italian versions of the interface strings the row quotes. The module in brackets, when there is one, shows where to find the term in the code. Entries follow the alphabetical order of the English term: the `ut` commands are under U and the `.orchestwin/` folder under O. In codes, "nnn" stands for a number of at least three digits, as in REQ-001.

The context of each term is in the pages on the [framework](framework/index.md) and on [validation with people](validation.md), and in the [`ut` reference](ut/index.md).

| Term | In the code or API | Meaning | In Italian |
|---|---|---|---|
| Acceptance criterion | `AC-nnn` | A verifiable condition the product must meet, with its verification method and the requirements and stories it checks; `ut test` tries it in the browsers. | Criterio di accettazione |
| Adherence | `direction_adherence` (`artifacts/design_distance.py`) | The check that says whether a mockup follows the axes of its visual direction; when it does not, the Studio flags it with "The mockup does not follow the direction on: …" but does not reject it. | Aderenza; "Il mockup non segue la direzione su: …" |
| Aligned point | decision `ALIGNED`, `.orchestwin/code/design.json` | The latest commit that a `ut verify` decision marked as aligned; for the design, the version the code is aligned with, written by `ut code` and by `ut align --from-design`. | Punto allineato |
| Alternative | `DesignAlternative`, `DES-001`…`DES-003` | A design proposal with its mockup; with the design system switched on there are three alternatives, and `DES-003` follows the Apple guidelines. | Alternativa |
| Approval | `APPROVE` (`HumanGateAction`) | The gesture with which the owner closes a gate on an exact version and hash; it lets the project use what is approved, and it is not a check with real users. | Approvazione |
| Archetype | `ArchetypeService` (`twins/archetypes.py`), stored as `PersonaProfile` | The kind of user the project means to represent; the twins are born from the confirmed archetypes, of which at most eight are active. | Archetipo |
| Brief | `ProjectBrief`, gate `PROJECT_BRIEF` | The structured description of the idea, composed through a dialogue with the model one question at a time (`BRIEF_QUESTION`, `BRIEF_SYNTHESIS`) and approved by the owner. | Brief |
| Candidate to verify | `validation_candidates` (`validation.py`) | A point the Studio marks as to be verified with people, born from the twins or their findings, with the linked twins, scenarios and design; it is not yet an operational hypothesis. | Candidata da verificare |
| Change in words | `DESIGN_CHANGE`, `DESIGN_ITERATION`, `ut design change` | A written request of up to 1,000 characters with which the model revises the chosen alternative or its mockup, changing only what the request asks for; the result is a new version to approve. | Modifica a parole |
| claude --print | provider `CLAUDE_CODE_CLI` (`models/claude_code_cli.py`) | The command line of Claude Code in non-interactive mode, with model and `effort` taken from the configuration, which the API uses for every generation on the subscription of whoever runs the Studio. | claude --print |
| Coding agent | `ut code --agent`, Claude Code by default | The external program that writes the code from the work order; it works with the account of whoever launches it and spends outside the Studio's ceilings. | Agente di programmazione |
| Contested | `CONTESTED` (`ReadableClaimStatus`) | The epistemic word for a claim on which sources or users disagree. | Contestato |
| Contrast | thresholds in `visual_catalog.py` and `generated_mockup_review.py` | The minimum ratio between text and background that the mockup review requires: 4.5:1 for text, 3:1 for large text and for the borders of controls, 7:1 and 4.5:1 in the high-contrast theme. | Contrasto |
| Conversation with a twin | `TWIN_CHAT`, `ut twins ask` | Questions and answers with a single twin, "Talk to the twin" in the web; every answer is a generation and stays a simulated hypothesis. | Conversazione con un twin; "Parla con il twin" |
| Coverage | `coverage`: `COMPLETE`, `PARTIAL` | Says whether an outcome covers an operational hypothesis in full or only in part; a partial outcome from a session with people makes the hypothesis "Uncertain". | Copertura; "Incerta" |
| Critique of an existing design | `DESIGN_CRITIQUE` (`artifacts/design_critique.py`), `ut design critique` | The twins' opinion, screen by screen, on a design brought in as a PNG or JPEG image of up to 5 MB or as a website captured at 1440 and 390 pixels; "Redraw as a mockup" turns it into a version to approve. | Critica di un design esistente; "Ridisegna come mockup" |
| Decision | `DecisionKind` (`projects/code_changes.py`) | The owner's choice on a commit examined by `ut verify`: `ALIGNED`, `DESIGN_CHANGE`, `REQUIREMENTS_CHANGE`, `CODE_TASKS` or `DISMISSED`. | Decisione |
| Definition | `requirements`, gate `REQUIREMENTS`, `ut definition` | The fourth step: scenarios, needs, stories, requirements, acceptance criteria and, when requested, journeys. | Definizione |
| Design & Evaluation | `design`, `DesignPackageVersion`, gate `DESIGN` | The fifth step: alternatives with their mockups and the twins' opinion, choice, changes, twin review and approval. | Design e valutazione |
| Design system | `DesignSystem`, `apple-hig` (`models/design_systems.py`) | Rules, palette and a pair of typefaces fixed in the code; the default, `apple-hig`, shown as "Apple guidelines" in the web, guides `DES-003`, and `ORCHESTWIN_DESIGN_SYSTEM=none` switches it off. | Sistema di design; "Linee guida Apple" |
| Design version | `DesignPackageVersion` (`artifacts/design_packages.py`) | A version of the design package with alternatives, choice and mockups; the web lists them under "Versions of the design (N)" with "Go back to this version". | Versione del design; "Versioni del design (N)", "Torna a questa versione" |
| Distance between the alternatives | `design_distance`, `STYLES_CLOSE` = 45 (`artifacts/design_distance.py`) | The measure from 0 to 100 of how much two mockups differ in their drawn style, read from the CSS and the HTML; below 45 the verdict is "Too close", from 45 up "They differ". | Distanza fra le alternative; "Troppo vicine", "Si distinguono" |
| Dossier | step `PACKAGE`, knowledge package (`/knowledge-packages`) | The sixth step: the published version of the project's knowledge, downloaded as a zip with a SHA-256 fingerprint, which becomes the `orchestwin/` folder. | Dossier |
| Element | `ELM-nnn`, attribute `data-elm` | A numbered part of a mockup screen that can be pointed at to ask for a change there only; `ut design show --elements` lists the elements that can be pointed at. | Elemento |
| Empirical source | `EMPIRICAL_RESEARCH` (`twins/epistemics.py`) | A source declared as empirical research, with its context, method and limits written down; it is the only kind that supports the outcome of a session with people. | Fonte empirica |
| Epistemic words | `ReadableClaimStatus` (`twins/representation.py`) | The five labels with which the interface says how well grounded a claim is: "Evidenced", "Inferred", "Hypothesized", "Contested" and "Unknown". | Parole epistemiche; "Documentato", "Dedotto", "Ipotizzato", "Contestato", "Sconosciuto" |
| Evidenced | `EVIDENCED` (`ReadableClaimStatus`) | The epistemic word for a claim supported by a source declared as empirical research. | Documentato |
| Fake Studio | `FakeStudio` (`src/test/python/cli/support/fake_studio/`) | The in-memory HTTP server that imitates the API for the tests of `ut`, with no database, model or network; since sprint 46 it is a package of 28 modules. | Studio finto |
| Finding | `SyntheticFinding` (`evaluation/findings.py`) | A twin's observation on a mockup, with criterion, severity, suggested action and a confidence declared by the model; for the code it is always simulated feedback. | Rilievo |
| Gate | `HumanGate`, `HumanGateType` (`workflow/gates.py`) | The point where a person decides on a version bound to its hash; the steps use `PROJECT_BRIEF`, `AGENT_TEAM`, `USER_MODELING`, `REQUIREMENTS` and `DESIGN`. | Gate |
| Generation | `model_proposal_generations` (`models/proposal_evidence.py`) | A call to the model with a task, a purpose and a response contract, recorded with the request, the raw response and its fingerprint, the tokens and the latency. | Generazione |
| Generation job | `GenerationJob` (`api/generation_jobs.py`) | A long generation that the API runs in the background when the request carries `Prefer: respond-async`; it lives in memory, at most four run at once per owner, and a restart of the API loses it. | Lavoro di generazione |
| Guard | `guard_contract46.py`, a sprint tool outside the repository | The script that compares the SHA-256 fingerprints of the files that fix what reaches the models or what is compared byte for byte, and fails if a changed file has no declaration with its reason. | Guard |
| Guided and expert mode | `GuidanceMode`: `GUIDED`, `EXPERT` (`identity/domain.py`) | Two ways of working, one step at a time with explanations or everything open from the start; the choice is made once per account and can no longer be changed. | Modalità guidata ed esperta |
| Hypothesized | `HYPOTHESIZED` (`ReadableClaimStatus`) | The epistemic word for a claim without empirical support, to be treated as a plausible hypothesis to verify. | Ipotizzato |
| Inferred | `INFERRED` (`ReadableClaimStatus`) | The epistemic word for a claim the model derived by inference (`MODEL_INFERRED`). | Dedotto |
| Journey | `JRN-nnn`, `ut definition journeys` | The phases a user goes through within a scenario; in the Definition they are optional and are added with "Request journeys". | Journey; "Richiedi journey" |
| Knowledge folder | `orchestwin/` (`knowledge/layout.py`) | The Dossier downloaded into the project's repository, at schema 3: one JSON and one Markdown document per step, tables, diagrams, schemas, `traceability/why.json`, the `ORCHESTWIN.md` index and the manifest. | Cartella di conoscenza |
| Learned observation | `OBS-nnn` (`knowledge/state.py`) | Something a twin learned from the development, kept by the owner after `ut twins update` or written with `ut twins learn`, and retired with `ut twins forget`. | Osservazione appresa |
| Local mode | `AccessMode.LOCAL_OWNER`, `ORCHESTWIN_ACCESS_MODE` (`config.py`) | The Studio without registration or login, with the account of whoever uses the computer; the default value is still `ACCOUNTS`, with registration and sign-in. | Modalità locale |
| Manifest | `orchestwin.json` | The file of the knowledge folder with the project, the version, the content fingerprint, the steps, the twins, the schemas and the fingerprint of every file. | Manifesto |
| MCP | `ut mcp`, server `orchestwin-twins` | The server that gives the editor's agents the twins, requirements, design, tasks and "Why?" read from the folder; the tools that spend (`ask_twin`, `review_changes`, `run_tests`) are switched on with `--spend`. | MCP; "Perché?" |
| Migration | Alembic revision, `orchestwin-migrate` | A step of the database schema; there are 76 revisions, from 0001 to 0075 plus 0005a. | Migrazione |
| Mockup | `GeneratedMockup`, `design/mockup.html` | The clickable HTML page of an alternative, with 2 to 8 screens and no scripts, written by the model with at most 48,000 output tokens. | Mockup |
| Mockup validators | `bind_generated_mockup` (`models/generated_mockup_drafts.py`) | The static checks that clean up a mockup and reject it if it breaks the contract (allowed elements, styles without external resources, contrast, reachable screens, covered requirements); a rejection goes back to the model with the reasons, for at most two attempts. | Validatori dei mockup |
| Need | `NED-nnn` | A need of the users in the Definition, tied to at least one scenario and to its sources. | Bisogno |
| Operational hypothesis | `HypothesisVersion`, `HYP-nnn` (`artifacts/human_validation.py`) | A candidate chosen by the owner and completed with a question or a task for a person, 1 to 24 "What to observe" points and the limits. | Ipotesi operativa; "Che cosa osservare" |
| `.orchestwin/` | local folder (`cli/project.py`) | The link between the folder and the Studio (`project.json`) and the local state of `ut`: approved steps, previews, work orders, test runs, alignments, study session. | `.orchestwin/` |
| Outcome | `ValidationOutcome`, `HVO-nnn` (`artifacts/human_validation.py`) | The result of a session on an operational hypothesis, "Confirmed", "Refuted" or "Uncertain", with a session code that carries no names and the exact quotation from the source. | Esito; "Confermata", "Smentita", "Incerta" |
| Owner | `owner_user_id` | The person the project belongs to, who takes every decision; in local mode it is the account of whoever uses the computer. | Proprietario |
| Persona | `PersonaProfile` (`twins/personas.py`), `ut twins persona` | In the code, the profile a twin is born from, that is the archetype; the "Persona" shown by the web and by `ut twins persona` is instead a readable view derived from the twin. | Persona |
| Perspectives | `team`, `Perspective`, gate `AGENT_TEAM` (`agents/perspectives.py`) | The second step: the competences through which the project is looked at (user experience, accessibility, software engineering, product, security) and the aspects "Web interface", "Services and data" and "Mobile". | Prospettive; "Interfaccia web", "Servizi e dati", "Mobile" |
| Point and ask | screen, element and zone target (`models/design_change.py`), zones (`artifacts/generated_mockup_zones.py`), `POST /design/opinions` (`api/design_opinions.py`), "Point at an element", "Ask the twins before applying" | The gesture that picks an element, a zone (ZON-nnn) or up to eight parts of one screen in the mockup, asks for a change to those parts only and has the twins give their opinion on it, before the change when you ask for it and after the change: "Helps", "Slows down" or "Blocks". | Indica e chiedi; "Indica un elemento", "Chiedi ai twin prima di applicare", "Aiuta", "Rallenta", "Blocca" |
| Proposal | `ProposalGenerator` (`models/proposal_generation.py`) | What the model generates for a step before the owner decides; in the interface it carries the label "AI proposal, not validated". | Proposta; "Proposta dell'AI, non validata" |
| Provider | `StructuredGenerationProviderKind` (`models/structured_generation.py`) | The kind of service that runs the generations; since 1 October 2026 the local configuration uses only `CLAUDE_CODE_CLI`, while the tests and the CI use `FAKE_DETERMINISTIC`. | Provider |
| Provisional | `TwinBasis.PROVISIONAL` (`twins/representation.py`) | The label of a twin without empirical support, because the brief and the owner's choices are not evidence about real users; with consistent empirical sources it becomes "Evidence based". | Provvisorio; "Fondato su evidenze" |
| Purpose | `purpose`, for example `DESIGN_DIRECTIONS` or `DESIGN_MOCKUP_HTML` | The reason for a generation, which selects the instruction, the response schema and, when configured, the model route. | Scopo |
| Re-anchoring | `sections/alignment`, `ut sections update`, "Update and confirm" | The update of a section left behind: the approved contents stay the same and are anchored to the new upstream versions. | Riaggancio; "Aggiorna e conferma" |
| Receipt | `GET /projects/{id}/model-usage` (`api/model_usage.py`) | The summary of every generation with task, purpose, provider, model, status, tokens and cost; in the web it appears as "Generations of the project", "Cost of the generations" and "Tokens". | Ricevuta; "Generazioni del progetto", "Costo delle generazioni", "Token" |
| Requirement | `REQ-nnn` | What the product must do, classified as functional, non-functional or constraint, with a MoSCoW priority, sources and the twins it serves. | Requisito |
| Restore | `ut design restore N`, "Go back to this version" | The return to an earlier version of the design: a new version identical to the chosen one is created, re-anchored to the current Definition and waiting for approval, with no work by the model. | Ripristino; "Torna a questa versione" |
| Rule | `owner_assertions`, `--rule` | A sentence from the owner that must stay true in later versions of the mockup; at most 5 new ones at a time and 20 in all. | Regola |
| Scenario | `SCN-nnn` | A situation of use played out by a twin, with initial conditions, a triggering event, steps and an expected outcome. | Scenario |
| Screen | `SCR-nnn` | A page of the mockup, reachable starting from `SCR-001`; a mockup can have from 2 to 8. | Schermata |
| Section | `Section`, `SectionState` (`projects/sections.py`) | A step already approved that can be reopened; its three states are "Up to date" (`FINE`), "Update available" (`UPDATE_AVAILABLE`) and "To update" (`TO_UPDATE`), while before the approval it shows "Waiting" or "Your turn". | Sezione; "A posto", "Aggiornamento disponibile", "Da aggiornare", "In attesa", "Tocca a te" |
| Session with people | `HUMAN_SESSION` | A session with real people on an operational hypothesis; its outcome requires an empirical source and is the only one that changes the state of the hypothesis. | Sessione con persone |
| Spending ceiling | `GenerationBudget`, `GENERATION_BUDGET_EXCEEDED` (`models/generation_budget.py`) | Three limits in microdollars, per generation, per project and in total, beyond which the API answers 402; with the zero prices of the example for Claude Code the estimate is zero and the ceilings never trip. | Tetto di spesa |
| Studio | `orchestwin-api` and the web | The local application: the FastAPI API on 127.0.0.1:8000, the Vue web on 8080 and PostgreSQL in Docker, all on the computer of whoever uses it. | Studio |
| Study session | `SES-…`, `ut activity start`, "Study session" | A period started and stopped by hand in which the web and `ut` record, with a closed vocabulary and no free text, what gets opened and how long the commands last. | Sessione di prova |
| Synthetic exercise | `SYNTHETIC_EXERCISE` | A session without people on a hypothesis, "Synthetic exercise, not empirical" in the web; its outcome stays on record apart and does not change the state of the hypothesis. | Prova sintetica; "Prova sintetica, non empirica" |
| Synthetic pre-validation | `TWIN_REVIEW`, findings `SyntheticFinding` | The evaluation made by the twins, which finds problems and prepares questions for people without replacing them; it is also the title of the review panel in the web. | Pre-validazione sintetica |
| Task | `TSK-nnn` (`projects/code_changes.py`), `ut tasks` | A piece of work for the code, born from a decision on a commit, from a check of the acceptance criteria or written by hand, which stays open, done or dropped (`OPEN`, `DONE`, `DROPPED`). | Compito |
| Test plan | `TEST_PLAN` (`models/test_planning.py`) | The paths the model writes, reading the application, to try the acceptance criteria; `ut test` reuses it as long as it still holds. | Piano dei test |
| Textual evidence | `EVD-nnn` (`projects/research_evidence.py`), `ut evidence` | An anonymised text, such as interview notes, of up to 24,000 characters, which the model compares with the twins and which the owner decides whether to let into the profile. | Evidenza testuale |
| Time spent | `dwell_seconds` (`activity.py`) | The time spent in a section during a study session, derived from the web's events. | Permanenza |
| Timeline | `GET /projects/{id}/activity` (`activity.py`), `ut activity` | The sequence of facts already recorded on a project, with times, gestures, gate rounds and generations per section, derived without any new store; in the web it is "Times and steps of the project". | Cronologia; "Tempi e passi del progetto" |
| Token | `input_tokens`, `output_tokens`, `reasoning_tokens` | The units of text that the model reads, writes and uses for reasoning in a generation, recorded in the receipt. | Token |
| Traceability | `ArtifactGraphNodeKind` (`artifacts/traceability.py`), `traceability/why.json` | The graph that links brief, perspectives, twins, evidence, Definition, design and mockup screens, and that the "Why?" walks through. | Tracciabilità; "Perché?" |
| Twin claim | `ProfileObservation` (`twins/epistemics.py`) | The value of a field of a twin's profile, for example its goals or context of use, with its provenance and one of the five epistemic words. | Affermazione del twin |
| Twin discussion | `TWIN_STATEMENT`, `DISCUSSION_SYNTHESIS` | The twins discuss the chosen design, answer one another and propose changes, and a moderator sums up agreements and disagreements; the web presents it as a simulation by the language model. | Discussione tra i twin |
| Twin review | `TWIN_REVIEW` (`api/design_loop.py`), `ut twins review` | After the choice, each twin reads the mockup in a call of its own and reports at most six findings, which the owner confirms or sets aside. | Revisione dei twin |
| Twin status | `UserTwinLifecycleStatus` (`twins/user_twins.py`) | How well grounded a twin is: "Initial proposal", "Based on the project", "Approved profile", "Based on real observations", "Validated with real observations". | Stato del twin; "Prima proposta", "Basato sul progetto", "Profilo approvato", "Basato su osservazioni reali", "Verificato con osservazioni reali" |
| Twin update | `TWIN_UPDATE`, `ut twins update` | The proposal of what each twin learned from its latest critiques, with one generation per twin, decided observation by observation with "Keep, edit or drop?". | Aggiornamento dei twin; "Tieni, correggi o scarta?" |
| Unknown | `UNKNOWN` (`ReadableClaimStatus`) | The epistemic word for a field whose value is unknown or on which the model abstained. | Sconosciuto |
| User story | `USR-nnn` | A user story told for a twin, with its goal, its benefit and the requirements it belongs to. | Storia |
| User Twin | `UserTwinProfile`, gate `USER_MODELING` (`twins/user_twins.py`) | The model of a kind of user, built from the brief, the confirmed archetypes and the evidence, which gives simulated opinions; it is not a person, and a project can have from 1 to 8. | User Twin |
| ut align | `KNOWLEDGE_ALIGNMENT`, `ALN-nnn` | From code to knowledge: the model reads the diff and proposes at most 12 updates to the Definition, the Design and the test plan, decided one by one; with `--from-design` it brings the differences of the approved design into the code. | ut align |
| ut code | `cli/flows/code_run.py` | Writes the work order and the MCP configuration, starts the coding agent after a gesture and makes no commits. | ut code |
| ut push | `cli/flows/push.py` | Brings back into the Studio the hand-made changes to the five step documents in the knowledge folder, one step at a time, as owner-supplied versions to approve. | ut push |
| ut test | `POST /projects/{id}/test-runs` | Tries the acceptance criteria in Chrome, in Firefox or in both on the application built outside the Studio, records the run and asks the twins to comment on it. | ut test |
| ut verify | `AlignmentStatus`: `ALIGNED`, `CODE_DRIFT`, `DESIGN_OUTDATED`, `REQUIREMENTS_OUTDATED` | Has the twins review the commits after the aligned point and asks the model for an alignment verdict; then the owner decides commit by commit. | ut verify |
| Verdict | `AlignmentStatus`, `DistanceVerdict`, `WORKS`, `SLOWS`, `BLOCKS` | The short judgement that closes an evaluation: one of the four states of `ut verify`, "They differ" or "Too close" for the distance, "Works for me", "Slows me down" or "Blocks me" in the critique. | Verdetto; "Si distinguono", "Troppo vicine", "Funziona per me", "Mi rallenta", "Mi blocca" |
| Version | `version_number`, `content_hash` | Every step saves immutable, numbered versions with their hash; a change, a re-anchoring or a restore always produces a new version. | Versione |
| Visual direction | `VisualDirection` (`artifacts/visual_directions.py`) | An idea of style written by the model, with rules and a value on five axes (layout, shapes, type, colour, density); among five candidates the Studio picks directions that differ on at least four axes. | Direzione visiva |
| Visual Studio Code extension | `editors/vscode` | The "OrchesTwin" panel, which reads `.orchestwin/` and the knowledge folder and writes the `ut` commands into the "OrchesTwin" terminal, where `ut` asks for confirmation before spending. | Estensione per Visual Studio Code |
| Why? | `why`, `traceability/why.json`, `ut why` | The panel that, for every artifact, shows "Where it comes from", the artifacts that depend on it and what is left "To verify with real people". | Perché?; "Da dove viene", "Da verificare con persone vere" |
| Work order | `prompt.md` in `.orchestwin/code/<date-time>/` | The text that `ut code` and `ut align --from-design` write for the coding agent, with the tasks, the request or the design differences to bring into the code. | Ordine di lavoro |
